# MultiAgentQA

Мультиагентная система автоматизации QA-процессов на базе [OpenCode](https://opencode.ai). Проект описывает и реализует сквозной QA Workflow: от анализа требований в Confluence до создания Jira-задач и тестовой модели в Qase.

Система построена на специализированных AI-агентах, каждый из которых имеет собственные полномочия, ограничения, Skills и контракты передачи результатов.

## Назначение

Проект автоматизирует повторяющийся цикл QA-подготовки:

1. Провести QA-ревью требований и выявить противоречия, неоднозначности, пробелы и риски.
2. Декомпозировать подтверждённые требования на задачи Jira.
3. Спроектировать тестовую модель и создать соответствующие сущности в Qase.
4. Проконтролировать качество и согласованность результатов, сформировать итоговый отчёт.

Ключевая идея — разделение ответственности. Управляющий агент не подменяет профильных специалистов, а координирует этапы, проверяет артефакты и следит за тем, чтобы подготовленные документы не выдавались за фактически выполненные операции.

## Участники Workflow

| Агент | Роль | Разрешённые операции |
|---|---|---|
| `orchestrator-agent` | Управляет последовательностью этапов, делегирует задачи, валидирует Artifacts, контролирует Quality Gates, формирует итоговый Workflow Report | Делегирование, чтение артефактов |
| `requirement-review-agent` | Проводит QA-анализ требований и готовит Requirement Review Artifact | Confluence READ |
| `task-design-agent` | Декомпозирует подтверждённые требования и создаёт Jira issues | Jira READ, Jira CREATE |
| `test-design-agent` | Проектирует тестовую модель и создаёт сущности Qase | Qase READ, Qase CREATE |

Агенты не пересекают границы своей области: Requirement Review Agent не создаёт сущности в Jira и Qase, Task Design Agent не изменяет Qase, Test Design Agent не изменяет Jira. Изменение или удаление существующих сущностей не входит в полномочия агентов и требует отдельного разрешения.

## Этапы Workflow

### Stage 1. Requirement Review

Orchestrator передаёт Requirement Review Agent источник и область требований. Агент читает материалы из Confluence, формирует рабочий контекст, анализирует требования по критериям Consistency, Clarity, Completeness, Testability и Risk Analysis, классифицирует найденные проблемы на блокирующие и неблокирующие и готовит Requirement Review Artifact.

Если обнаружены противоречия или требуется бизнес-решение, Workflow останавливается и вопрос эскалируется ответственному лицу.

### Stage 2. Task Design и Test Design

После прохождения Requirement Review Gate один и тот же валидированный Artifact получают два независимых агента:

- **Task Design Agent** декомпозирует требования, проверяет возможные дубликаты и создаёт Jira issues.
- **Test Design Agent** проектирует тестовую модель, проверяет дубликаты и создаёт suites и test cases в Qase.

Агенты могут выполняться параллельно или последовательно. Результат одного не является обязательным входом для другого.

### Stage 3. Final Quality Gate

Orchestrator независимо проверяет:

- прослеживаемость результатов до исходных требований;
- соответствие артефактов установленным контрактам;
- фактическое создание сущностей и сохранение их идентификаторов;
- отсутствие противоречий между результатами этапов.

### Stage 4. Final Reporting

Формируется итоговый Workflow Report со статусом `SUCCESS`, `PARTIAL`, `FAILED` или `REQUIRES_HUMAN_DECISION`, перечнем созданных сущностей, ошибок, ограничений и вопросов для эскалации.

## Artifacts

Результаты работы агентов сохраняются в каталог `artifacts/` по схеме:

```
artifacts/{artifact_name}/{artifact_name}-{version}-{date}.md
```

| Artifact | Producer | Consumers |
|---|---|---|
| Requirement Review Artifact | Requirement Review Agent | Orchestrator, Task Design Agent, Test Design Agent |
| Jira Tasks Artifact | Task Design Agent | Orchestrator |
| Test Model Artifact | Test Design Agent | Orchestrator |
| Workflow Report | Orchestrator | — |

Artifact фиксирует подготовленный результат, а не факт выполнения операции. Успешное создание сущности подтверждается только ответом соответствующего инструмента.

## Принципы работы

Все агенты обязаны соблюдать правила из [`AGENTS.md`](AGENTS.md). Основные из них:

- **Accuracy** — использовать только подтверждённую информацию, не выдумывать требования и результаты.
- **Traceability** — сохранять связь результатов с исходными требованиями и источниками.
- **Minimal Changes** — не изменять существующие данные и артефакты без явного разрешения.
- **Scope Control** — выполнять только задачи в рамках своей области ответственности.
- **No Silent Failure** — не скрывать ошибки и не выдавать частичный результат за завершённый.
- **Separation of Responsibilities** — не выполнять работу другого агента без отдельного поручения.
- **Escalation** — передавать бизнес-противоречия и неоднозначности ответственному лицу, а не решать их самостоятельно.

## Требования и настройка

Для работы проекта необходимы:

- OpenCode с поддержкой агентов, skills и plugins;
- доступ к Confluence через REST API;
- подключённые MCP-интеграции Jira и Qase (для соответствующих этапов).

Инструмент `.opencode/tools/confluence.ts` получает страницу Confluence по `pageId` и использует переменные окружения:

| Переменная | Назначение |
|---|---|
| `CONFLUENCE_URL` | Базовый URL инстанса Confluence |
| `CONFLUENCE_EMAIL` | Email пользователя для Basic Auth |
| `CONFLUENCE_API_TOKEN` | API token пользователя |

Значения переменных не должны попадать в репозиторий или артефакты.

## Запуск

Агенты и skills подхватываются OpenCode автоматически из каталога `.opencode/`. Workflow запускается через Orchestrator Agent с Task Prompt, содержащим параметры задачи:

- `application_name` — название приложения или проекта;
- `requirements_source` — ссылка, ID или иной идентификатор источника требований в Confluence;
- `requirements_scope` — страницы, разделы или требования для анализа;
- `jira_project` — идентификатор проекта Jira;
- `qase_project` — идентификатор проекта Qase;
- `additional_context` — дополнительные сведения и ограничения.

Не все параметры обязательны; отсутствующие значения не подменяются предположениями — при необходимости они запрашиваются у пользователя.

## Ограничения

- Агенты не изменяют исходные требования и не принимают бизнес-решения.
- Агенты не выполняют операции UPDATE и DELETE над сущностями Jira и Qase.
- Массовые и необратимые операции требуют явного разрешения.
- При недоступности источника или неоднозначном результате операции фиксируется ограничение и выполняется эскалация.
