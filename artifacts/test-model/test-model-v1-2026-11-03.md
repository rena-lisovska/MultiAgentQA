| Обработка системных ошибок (5xx, таймаут, сеть), блокировка кнопки Login при запросе | Ожидаемое поведение не определено (NB-07, MIS-05, OQ-15) |
| Локализация и выбор языка интерфейса | Не определено (NB-08, OQ-17) |

| Автоматизированные тесты, Test Runs, Jira-задачи | Вне Scope роли test-design-agent |

### 2.3. Scope Limitations и принятые ограничения

1. **Точные тексты сообщений** проверяются как эталонные строки согласно VAL-06/VAL-07 («Это поле обязательно», «Введите корректный email», «Неверный email или пароль»), оговорка NB-08.
2. **Тестовые данные** (зарегистрированные/незарегистрированные учётные записи) не описаны требованиями (MIS-02, RSK-07); в тест-кейсах используются фиксированные fixture-значения, которые обязано предоставить тестовое окружение.
3. **«Закрытие браузера»** (AC-14) операционализируется минимально: полное закрытие браузера (все окна, завершение процесса) и повторный запуск. Граничные трактовки (вкладка/окно/профиль/перезапуск ОС) и семантика 30-дневного срока (NB-06, BND-11, BND-12) не проверяются.
4. **Срок 30 дней** (AC-13) проверяется по сроку действия сохранённых в браузере данных авторизации и по сохранению авторизации после перезапуска браузера; продление срока при активности и поведение по истечении срока (NB-06) не проверяются.
5. **Контрол выхода из системы** требованиями не описан (NB-05, MIS-03): тест-кейс проверяет результат выхода (переход на экран авторизации), а не расположение контрола.
6. **URL личного кабинета** не предполагается: в тест-кейсе используется адрес, зафиксированный по факту навигации до выхода.
7. Проверка «запрос на авторизацию не отправляется» (AC-02, AC-03) выполняется по панели сетевых запросов браузера — способ верификации, а не новое требование. Для AC-04 аналогичное утверждение **не формулируется**, так как отправка запроса при ошибке формата не определена (NB-03, OQ-02).
8. Для REQ-06 проверяются только допустимые границы 8 и 64 символа (AC-09). Значения 7 и 65 символов исключены (BLK-01, AC-08).

## 3. Test Strategy

### 3.1. Используемые виды тестирования

| Вид тестирования | Применение |
|---|---|
| Positive Testing | AC-05 (успешный вход), AC-13/AC-14 (Remember me), AC-09 (допустимые граничные длины) |
| Negative Testing | AC-02, AC-03 (пустые поля), AC-06 (незарегистрированный email), AC-07 (неверный пароль), AC-15 (доступ к личному кабинету после выхода) |
| Validation Testing | AC-02, AC-03, AC-04 — проверка сообщений валидации и их расположения под соответствующим полем |
| Boundary Value Testing | AC-09 — нижняя (8) и верхняя (64) допустимые границы длины пароля |
| Equivalence Partitioning | Классы: корректный/некорректный формат email; зарегистрированный/незарегистрированный email; правильный/неправильный пароль допустимой длины |
| State Transition Testing | Состояния сессии: не авторизован → авторизован (AC-05) → выход → не авторизован (AC-15); сохранение состояния после перезапуска браузера (AC-13, AC-14) |
| Integration Testing | Взаимодействие формы входа с сервисом авторизации и контроль доступа к личному кабинету (AC-05, AC-06, AC-07, AC-15) — в объёме, наблюдаемом через UI |
| Error Handling Testing | Только обработка ошибок валидации и ошибки «Неверный email или пароль»; системные ошибки исключены (NB-07) |

Не применялись: Performance, Security (кроме наблюдаемого контроля доступа), Compatibility, Usability — соответствующие требования отсутствуют.

### 3.2. Обоснование подхода

- Приоритет отдан **критическому бизнес-потоку** (успешный вход) и **проверкам, отказ которых приводит к несанкционированному доступу** (AC-06, AC-07, AC-15). Это соответствует рискам RSK-02, RSK-03, RSK-04 из Requirement Review.
- **Валидационные проверки** (AC-02…AC-04) покрываются изолированно, по одному нарушению на тест-кейс, поскольку порядок и совместный показ сообщений не определены (NB-02). Комбинированные сценарии не создаются.
- **Границы** покрываются только в допустимой части диапазона (AC-09), так как поведение вне диапазона конфликтует между REQ-05 и REQ-06 (BLK-01, CNF-01).
- **Состояние сессии** (Remember me, выход) покрывается базовыми потоками без проверок на границе срока и без управления временем — требования не определяют семантику (NB-06, BLK-02).
- Каждый тест-кейс проверяет одно поведение и имеет однозначный проверяемый Expected Result, выводимый из Artifact.

### 3.3. Основные направления покрытия

1. Наличие и корректность элементов формы (базовая предпосылка всех остальных проверок — DEP-01).
2. Клиентская валидация: обязательность полей и формат email.
3. Результат обращения к сервису авторизации: успех, отказ при незарегистрированном email, отказ при неверном пароле.
4. Допустимые границы длины пароля.
5. Жизненный цикл сессии: сохранение (Remember me), завершение по закрытию браузера, завершение по выходу, недоступность личного кабинета после выхода.

### TC-01 — Состав формы авторизации

- **test_ref:** TC-01
- **scenario:** SC-01
- **title:** Состав формы авторизации: поля Email, Password, чекбокс Remember me и кнопка Login
- **description:** Проверка наличия и названий элементов формы входа. Источник: REQ-01 / AC-01. Состояние чекбокса Remember me по умолчанию не проверяется (NB-04).
- **preconditions:** 1. Пользователь не авторизован. 2. Страница авторизации доступна.
- **steps:**
  1. Открыть страницу авторизации. → Страница авторизации отображается, форма входа доступна.
  2. Проверить наличие и названия полей ввода Email и Password. → Отображаются поле ввода Email и поле ввода Password с указанными названиями.
  3. Проверить наличие чекбокса Remember me. → Отображается чекбокс с названием Remember me.
  4. Проверить наличие кнопки Login. → Отображается кнопка с названием Login.
- **expected_result:** Форма авторизации содержит поле Email, поле Password, чекбокс Remember me и кнопку Login с указанными названиями.
- **priority:** HIGH
- **severity:** major
- **test_type:** functional
- **source_requirements:** REQ-01 → AC-01
- **blocker/open question:** нет (состояние Remember me по умолчанию — NB-04, не проверяется)

### TC-02 — Пустое поле Email

- **test_ref:** TC-02
- **scenario:** SC-02
- **title:** Пустое поле Email: сообщение «Это поле обязательно» и отсутствие запроса на авторизацию

- **priority:** HIGH
- **severity:** major
- **test_type:** functional
- **source_requirements:** REQ-02 → AC-02
- **blocker/open question:** нет (строка из пробелов — NB-02, не проверяется)

1. **BLK-01** (Critical): не определено ожидаемое сообщение при зарегистрированном email и пароле вне диапазона 8…64 (AC-08, NF-07, BND-01, BND-04) → покрытие отсутствует.

4. **NB-02**: порядок и совместность сообщений валидации не определены → комбинированные негативные сценарии не созданы (по решению Orchestrator).

6. **NB-06**: семантика 30-дневного срока и «закрытия браузера» → проверяются базовые потоки; для шагов с временем требуется управление состоянием сессии/данных браузера.
7. **MIS-02 / RSK-07**: требованиями не описан способ создания учётных записей → исполнимость кейсов TC-05…TC-11 зависит от наличия предсозданных тестовых учётных записей с известными паролями (включая заведомо неверный пароль допустимой длины).
8. **OQ-18**: код проекта `AUTH` требованиями не подтверждён; сущности создаются в проекте, переданном Orchestrator.
9. Панель сетевых запросов браузера (TC-02, TC-03) — способ верификации требования «запрос не отправляется», а не дополнительное требование.
