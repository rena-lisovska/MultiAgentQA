## 3. Test Strategy

### 3.1. Принятый подход

Выбран вариант «покрытие по логическим блокам требований с полным набором позитивных, негативных и граничных проверок внутри блока». Альтернативы, которые рассматривались и отклонены:

- покрытие по типам проверок (позитивные/негативные/граничные разделы) — отклонено: нарушает правило Skill о выделении Test Suites по требованиям, а не по типам проверок, и разносит проверки одной функциональной области по разным разделам;
- покрытие «только критические потоки» (вход, успех, неверные учётные данные) — отклонено: оставляет без покрытия правила формата Email и пароля, для которых Artifact задаёт наблюдаемый эффект (`VR-01 … VR-14`, `BD-01 … BD-09`), и не даёт прослеживаемости по 36 требованиям.

Структура Test Suites повторяет 7 смысловых разделов требований, что обеспечивает однозначное отнесение каждого тест-кейса к одному разделу и совпадение границ раздела с границами блока требований.

### 3.2. Техники и типы проверок

| Функциональная область | Техники | `test_type` тест-кейсов | Обоснование |
|---|---|---|---|
| Состав формы (REQ-01 … REQ-04) | Проверка состава и исходного состояния UI | `POSITIVE` | Требование задаёт перечень элементов и состояние чекбокса по умолчанию |
| Обязательность полей (REQ-05 … REQ-11) | `Equivalence Partitioning` (пусто / только пробелы / заполнено), проверка одновременного вывода ошибок | `NEGATIVE`, `POSITIVE`, `VALIDATION` | Требования задают сообщение «Это поле обязательно» и правило одновременного показа ошибок; решение `BLK-01` задаёт единственный ожидаемый результат для пароля из пробелов |
| Формат Email (REQ-12 … REQ-21) | `Equivalence Partitioning` по правилам формата, `Boundary Value Analysis` (253/254/255), проверка белого списка символов | `POSITIVE`, `NEGATIVE`, `BOUNDARY` | Каждое правило раздела 3 Artifact имеет наблюдаемый эффект; границы длины заданы `BD-01` |
| Формат пароля (REQ-22 … REQ-26) | `Boundary Value Analysis` (7/8/64/65), `Equivalence Partitioning` по белому списку символов | `BOUNDARY`, `NEGATIVE`, `POSITIVE` | Границы заданы `BD-03`; белый список — решением `BLK-02` |
| Успешная авторизация (REQ-27) | Позитивный поток с наблюдаемым результатом (URL `/dashboard`) | `POSITIVE` | `AC-14` задаёт единственный ожидаемый результат |
| Неуспешная авторизация (REQ-28 … REQ-30) | `Equivalence Partitioning` по причинам отказа (незарегистрированный Email, неправильный пароль, отличие только в регистре) | `NEGATIVE` | Все три причины ведут к одному сообщению (`BR-12`), но различаются входными данными и должны проверяться отдельно |
| Remember me (REQ-31 … REQ-36) | `State Transition Testing` (перезапуск браузера, истечение срока, работа с вкладками), проверка ограничения области действия | `POSITIVE`, `STATE_TRANSITION`, `NEGATIVE` | Требования задают состояния и условия их завершения |

`INTEGRATION`, `ERROR_HANDLING` и `RISK_BASED` не применялись: интеграционных зависимостей с наблюдаемым эффектом Artifact не задаёт (данные `DEP-01 … DEP-05` отсутствуют), обработка отказов сервиса выведена из области (`BLK-05`), а риск-ориентированные тест-кейсы не создавались, так как активные находки `NB-09 … NB-12` требованиями не являются.

### 3.3. Правила приоритизации

`HIGH` назначался, если проверка относится к входной точке авторизации и её отказ блокирует основной поток (обязательность, формат полей, успешный вход, неверные учётные данные) либо если поведение определено решением ответственного лица по блокирующей находке (`BLK-01 … BLK-04`) и его регресс наиболее вероятен. `MEDIUM` — проверки отдельных правил формата, границ и поведения `Remember me` за пределами основного потока. `LOW` не назначался: все проверки области следуют из требований и влияют на наблюдаемый результат входа. `priority_source` указан в каждом тест-кейсе (`RISK_ANALYSIS` либо `REQUIREMENT_REVIEW`).

### 3.4. Передача `priority` и `test_type` в Qase

Проект `AUTH` не имеет кастомных полей (`qase_project_context`: `custom_fields.total = 0`), проектных правил маппинга не передано. Справочник Qase для поля `type` (см. `system_field`) не содержит значений Skill (`POSITIVE`, `NEGATIVE`, `BOUNDARY`, `VALIDATION`, `STATE_TRANSITION`) — эквивалентов нет. Принятое решение:

- `priority` Skill (`HIGH` / `MEDIUM` / `LOW`) передан в нативное поле Qase `priority` (`high` = 1, `medium` = 2);
- точное значение `test_type` Skill передано в поле Qase `tags` без изменения значения (Qase приводит теги `positive` / `negative` к нижнему регистру — это поведение Qase, значение не искажается);
- нативное поле Qase `type` заполнено значением `functional` для всех тест-кейсов: все проверки области — функциональное поведение формы авторизации;
- нативное поле Qase `behavior` заполнено `positive` только для тест-кейсов `POSITIVE` и `negative` только для тест-кейсов `NEGATIVE`; для `BOUNDARY`, `VALIDATION`, `STATE_TRANSITION` поле оставлено незаполненным, так как такие тест-кейсы содержат и проходящие, и непроходящие значения.

Кастомные поля не создавались. Соответствие `test_type` ↔ теги зафиксировано в разделе 7 в каждом тест-кейсе.

### 3.5. Что сознательно не покрывается

1. Отказ сервиса авторизации (`NF-12`) — вне области по решению `BLK-05`.
2. Проверка точного текста сообщений при нарушении формата — текст не зафиксирован (`NB-14`, `OQ-05`, L-01).
3. Защита от перебора, завершение сессии по бездействию, совместимость с браузерами, производительность — требований нет (`NB-09 … NB-12`, L-07).
4. Выход из системы и его влияние на сохранённую авторизацию — не описано (`NB-05`, L-08).
5. Маскирование пароля и ограничения на его отображение — не описано (`NB-03`, `NB-11`, L-06).
6. Неопределённые границы формата Email (позиция точки в имени пользователя, подряд идущие точки, дефис в начале/конца домена, лимит длины после удаления пробелов) — `NB-06`, `NB-07`, L-09.
7. Поведение в приватном окне и после очистки данных браузера — `NB-02`, L-03.
