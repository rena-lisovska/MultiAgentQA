### 2.3. Краткий итог анализа

Требования описывают единый поток авторизации: состав формы, обязательность полей, формат Email, длину и допустимые символы пароля, успешный и неуспешный вход, поведение флага `Remember me`. Основные позитивные и негативные потоки в целом прослеживаются до текста требований и пригодны для декомпозиции.

Ключевые дефекты (исходные, выявленные в v1):
- одно и то же состояние пароля (только пробелы) приводило к взаимоисключающим результатам (`CONFLICT`);
- перечни допустимых символов Email и Password были сформулированы как разрешение и не задавали поведение для символов вне перечня (`AMBIGUITY`);
- не была определена регистрозависимость пароля при проверке (`AMBIGUITY`);
- для нарушений формата Email не был задан текст сообщения (`MISSING_INFORMATION`);
- не было определено поведение при отказе сервиса авторизации (`MISSING_INFORMATION`).

**Статус в v2:** все пять блокирующих находок закрыты решениями ответственного лица от 2026-11-14 (SR-02) и переведены в раздел §10 «Resolved by Human Decision» с сохранением ID и исходных описаний. Блокирующих находок в v2 нет. Решение по BLK-04 закрывает вопрос о количестве и факте сообщения, но не фиксирует его текст — остаточная неопределённость оформлена как NB-14 и OQ-05. Решение по BLK-05 выводит сценарий отказа сервиса из области текущих требований.

Отсутствуют требования к защите от перебора, к сроку жизни неактивной сессии, к маскированию поля пароля. Не описан выход (logout). Эти пробелы остаются рисками и вопросами, а не добавленными требованиями.

### BLK-01 — Пароль из одних пробелов: взаимоисключающие результаты

- **Класс в v1:** `BLOCKING` → **Класс в v2:** `RESOLVED BY DECISION`
- **Статус:** `RESOLVED` (2026-11-14, SR-02)
- **Тип:** `CONFLICT`
- **Приоритет (исходный):** `HIGH`
- **Связанные требования:** REQ-05, REQ-06, REQ-11, REQ-22, REQ-26 (BD-06, BD-07)
- **Подтверждающие фрагменты:**
  - §2: «Если поле пустое или содержит только пробелы, отображается сообщение «Это поле обязательно».»
  - §2: «При наличии ошибок запрос на авторизацию не отправляется.»
  - §4: «Пароль должен содержать от 8 до 64 символов включительно.»
  - §4: «Пробелы в пароле разрешены.»
- **Описание проблемы:** для пароля, состоящего только из пробелов (например, 8 пробелов), источник одновременно задаёт два несовместимых результата. По REQ-06 значение «содержит только пробелы» → показывается «Это поле обязательно», запрос не отправляется. По REQ-22 и REQ-26 то же значение содержит 8 символов (в диапазоне 8–64) и пробелы разрешены → проверка длины пройдена, ошибка обязательности не возникает, и при отсутствии других ошибок запрос на авторизацию отправляется. Правило приоритета между этими нормами в источнике отсутствует.
- **Влияние на разработку и тестирование:** невозможно определить, должен ли запрос на авторизацию отправляться для такого значения; разные реализации будут вести себя по-разному, а тест-кейс на пароль из пробелов не имеет единственного ожидаемого результата. Затрагивает входную точку функциональности.
- **Вопрос (исходный, закрыт):** считается ли пароль, состоящий только из пробелов, незаполненным полем (ошибка «Это поле обязательно») или допустимым значением длиной 8–64 символа, которое отправляется на авторизацию?
- **Решение ответственного лица (2026-11-14, SR-02):** пароль, состоящий только из пробелов (например, 8 пробелов), считается **допустимым значением**: проверка длины 8–64 проходит, пробелы разрешены, запрос на авторизацию отправляется, ошибка «Это поле обязательно» для такого значения **не показывается**.
- **Что уточнено в Artifact:** BR-02 (исключение для `Password`), BR-09, AC-03, VR-01, VR-14, BD-06, BD-07, NF-08 → PF-07, OQ-01 (закрыт).
- **Остаточные ограничения:** нет. Решение задаёт единственный ожидаемый результат для значения из одних пробелов.

### BLK-02 — Перечни допустимых символов Email и Password не задают поведение для символов вне перечня

- **Класс в v1:** `BLOCKING` → **Класс в v2:** `RESOLVED BY DECISION`
- **Статус:** `RESOLVED` (2026-11-14, SR-02)
- **Тип:** `AMBIGUITY`
- **Приоритет (исходный):** `HIGH`
- **Связанные требования:** REQ-15, REQ-16, REQ-19, REQ-25, REQ-26 (VR-05, VR-13, BD-09)
- **Подтверждающие фрагменты (дословно):**
  - §3: «Имя пользователя может содержать латинские буквы строчные (a-z) и прописные (A-Z), цифры от 0 до 9, специальные символы: ! # $ % ^ & * ( ) _ + - = [ ] { } ; : ' " , . < > / ? \ | ~`»
  - §3: «Домен может содержать латинские буквы, цифры, дефисы и точки.»
  - §3: «Email не должен содержать кириллические символы.»
  - §4: «Пароль может содержать латинские буквы строчные (a-z) и прописные (A-Z), цифры от 0 до 9, специальные символы: ! @ # $ % ^ & * ( ) _ + - = [ ] { } ; : ' " , . < > / ? \ | ~`»
  - §4: «Пробелы в пароле разрешены.»
- **Описание проблемы:** перечни сформулированы как разрешение («может содержать»), а не как исчерпывающий набор допустимых символов. Из текста не следует, что символ вне перечня запрещён. Для пароля это подтверждается тем, что пробел одновременно отсутствует в перечне и разрешён отдельным пунктом, то есть перечень не является закрытым. Для Email запрет задан только для кириллицы, иных запретов на символы вне перечня нет. В результате ожидаемое поведение для символов, не входящих ни в перечень, ни в явный запрет (например, символов других алфавитов, эмодзи, иных типографских символов), не определено — как для прохождения проверки, так и для сообщения об ошибке (текст такого сообщения также не задан).
- **Влияние на разработку и тестирование:** разработка не может выбрать между валидацией по белому списку и валидацией только по явным запретам; тест-дизайн не может построить проверки на недопустимые символы ни для Email, ни для пароля, так как нет ни однозначного ожидаемого результата, ни текста сообщения.
- **Вопрос (исходный, закрыт):** являются ли перечни допустимых символов Email и пароля исчерпывающими (любой символ вне перечня не допускается) или описательными (запрещены только явно перечисленные ограничения)? Какое сообщение отображается при недопустимых символах и для какого поля?
- **Решение ответственного лица (2026-11-14, SR-02):** перечни допустимых символов Email и пароля — **исчерпывающий белый список**. Любой символ вне перечня недопустим: для Email — нарушение формата; для Password — нарушение формата.
- **Что уточнено в Artifact:** BR-01, AC-09, VR-05, VR-13, BD-09, OQ-02 (закрыт).
- **Остаточные ограничения:** решение определяет только квалификацию нарушения формата и не задаёт текст сообщения при недопустимых символах. Для Email этот текст охвачен решением по BLK-04 и остаточной находкой NB-14; для Password текст сообщения при нарушении белого списка решением не задан — отражено в NB-14 и VR-13. OQ-03 закрыт в части правила квалификации, но остаётся частью открытого вопроса о тексте (NB-14).

### BLK-03 — Не определена регистрозависимость пароля при проверке

- **Тип:** `AMBIGUITY`

- **Описание проблемы:** для Email правило регистронезависимого сравнения задано явно, для пароля такого правила нет. Понятия «правильный пароль» и «неправильный пароль» не определены как сравнение с учётом или без учёта регистра. - **Что уточнено в Artifact:** AC-14, AC-15, NF-09, OQ-04 (закрыт).
- **Остаточные ограничения:** нет. Решение задаёт единственный ожидаемый результат для отличия только в регистре.

### BLK-04 — Для нарушений формата Email не заданы сообщения об ошибках

- **Класс в v1:** `BLOCKING` → **Класс в v2:** `RESOLVED BY DECISION` (частично, с остаточной неопределённостью)
- **Статус:** `RESOLVED` (2026-11-14, SR-02)
- **Тип:** `MISSING_INFORMATION`
- **Приоритет (исходный):** `HIGH`
- **Связанные требования:** REQ-07, REQ-11, REQ-13 … REQ-20 (AC-08, AC-09, AC-10, VR-03 … VR-10)
- **Подтверждающие фрагменты:**

  - §2: «При наличии ошибок запрос на авторизацию не отправляется.»
  - §3: перечислены только правила формата (REQ-12 … REQ-20), ни одного сообщения об ошибке не задано.
  - Для сравнения, тексты заданы только для двух случаев: §2 «Это поле обязательно», §4 «Пароль должен содержать от 8 до 64 символов».
- **Описание проблемы:** раздел 3 задаёт девять правил формата Email, но не задаёт ни текста сообщения при их нарушении, ни требования о том, что при неверном формате Email отображается сообщение. Требование REQ-07 («показывает все обнаруженные ошибки») подразумевает отображение ошибок, однако их содержание и количество (одно обобщённое сообщение на все нарушения формата или отдельное сообщение на каждое нарушение) не определены. Затрагивает основной поток и входную точку функциональности.
- **Вопрос (исходный, частично закрыт):** какие сообщения отображаются при нарушении правил формата Email, является ли сообщение единым для всех нарушений формата или отдельным для каждого, и совпадает ли оно с сообщением «Это поле обязательно»?

- **Остаточные ограничения:** текст сообщения не зафиксирован → оформлено как активная находка `NB-14` (`NON_BLOCKING`) и открытый вопрос OQ-05. Проверки на точный текст сообщения не проектируются; проверяются факт отображения одного общего сообщения и отсутствие отправки запроса.

### BLK-05 — Не определено поведение при отказе сервиса авторизации

- **Класс в v1:** `BLOCKING` → **Класс в v2:** `RESOLVED BY DECISION`
- **Статус:** `RESOLVED` (2026-11-14, SR-02)
- **Тип:** `MISSING_INFORMATION`
- **Приоритет (исходный):** `MEDIUM`
- **Связанные требования:** REQ-27, REQ-28, REQ-29, REQ-30

  - §5: «…система должна авторизовать пользователя и перенаправить его на главную страницу личного кабинета /dashboard.»

Поведение при недоступности сервиса авторизации (ошибка сервера, сетевой сбой, таймаут) не описано: не определено ни сообщение, ни состояние полей, ни факт сохранения или несохранения введённых значений. Поскольку отправка запроса прямо предусмотрена требованиями, этот сценарий является частью описанного потока, и его ожидаемый результат из текста не выводится.

- **Остаточные ограничения:** сценарий остаётся неописанным в требованиях; это принятое ограничение области, а не дефект, требующий устранения. Потребители Artifact не должны выводить из него требования или проверки для этого сценария. Если в будущем сценарий войдёт в область, потребуется отдельное требование.

- **Связанные требования:** REQ-15, REQ-16, REQ-19
- **Подтверждающие фрагменты:** §3: «Имя пользователя может содержать латинские буквы строчные (a-z) и прописные (A-Z), цифры от 0 до 9, специальные символы: …»; §3: «Домен может содержать латинские буквы, цифры, дефисы и точки.»; §3: «Email не должен содержать кириллические символы.»
- **Описание проблемы:** при исчерпывающем перечне символов отдельный запрет кириллицы не добавляет нового ограничения, но создаёт вторую точку изменения правил: при расширении перечня запрет может начать противоречить ему.
- **Влияние на разработку и тестирование:** дублирующие правила увеличивают риск расхождения реализации и тест-модели при изменении требований.
- **Рекомендация:** явно обозначить перечень символов как исчерпывающий и указать, является ли правило о кириллице самостоятельной явной проверкой или следствием перечня. Смысл требований при этом не меняется (связано с BLK-02).

### NB-09 — Отсутствует ограничение числа неуспешных попыток входа

- **Класс:** `NON_BLOCKING`
- **Тип:** `RISK`
- **Приоритет:** `HIGH`
- **Связанные требования:** REQ-28, REQ-29
- **Подтверждающий фрагмент:** §6: «При вводе незарегистрированного Email или неправильного пароля система должна: … Показать сообщение «Неверный email или пароль»; … Не авторизовать пользователя; … Сохранить введённые значения в полях `Email` и `Password`.»
- **Описание проблемы:** раздел 6 описывает только сообщение и отказ в авторизации; реакции системы на повторяющиеся неуспешные попытки (счётчик, задержка, временная блокировка, капча) в источнике нет. Это не дефект формулировки, а отсутствие нефункционального ограничения.
- **Влияние на разработку и тестирование:** проверки устойчивости к перебору не могут быть спроектированы по требованию; при отсутствии ограничения входная точка авторизации остаётся без описанной защиты.
- **Вопрос:** предусмотрены ли ограничения на количество или частоту неуспешных попыток входа и каково ожидаемое поведение при их превышении?

### NB-10 — Не определено ограничение времени жизни неактивной сессии без `Remember me`

- **Класс:** `NON_BLOCKING`
- **Тип:** `RISK`
- **Приоритет:** `MEDIUM`
- **Связанные требования:** REQ-35, REQ-36
- **Подтверждающие фрагменты:** §7: «Авторизованная сессия завершается после закрытия браузера;»; §7: «Закрытие отдельной вкладки, открытие новой вкладки или переход между страницами не завершают сессию.»
- **Описание проблемы:** для режима без `Remember me` единственным условием завершения сессии названо закрытие браузера. Ограничение по бездействию при открытом браузере не описано, то есть сессия может оставаться активной неограниченно долго. Это отсутствие нефункционального ограничения, а не противоречие в тексте.
- **Влияние на разработку и тестирование:** проверки автоматического завершения по бездействию не могут быть спроектированы; риск неконтролируемого времени жизни сессии на общем устройстве.
- **Вопрос:** предусмотрено ли автоматическое завершение сессии по истечении времени бездействия при открытом браузере без `Remember me`?

### NB-11 — Сохранение введённого пароля в поле после неуспешной попытки

- **Класс:** `NON_BLOCKING`
- **Тип:** `RISK`
- **Приоритет:** `MEDIUM`
- **Связанные требования:** REQ-30
- **Подтверждающий фрагмент:** §6: «Сохранить введённые значения в полях `Email` и `Password`.»
- **Описание проблемы:** требование прямо предписывает оставлять введённый пароль в поле после неуспешной попытки. Это осознанное требование, но оно создаёт риск раскрытия пароля (визуально, при демонстрации экрана, через автозаполнение) и расширяет поверхность его присутствия в UI.
- **Влияние на разработку и тестирование:** требуется отдельная проверка того, что значение пароля остаётся в поле и при этом не раскрывается; необходимость такой проверки следует из требования REQ-30, но связанные с ней ограничения безопасности в источнике не заданы.
- **Вопрос:** должны ли сохраняться в поле оба значения, включая пароль, и какие ограничения на отображение пароля при этом действуют?

### NB-12 — Отсутствуют требования к совместимости с браузерами и производительности

- **Класс:** `NON_BLOCKING`
- **Тип:** `RISK`
- **Приоритет:** `LOW`
- **Связанные требования:** REQ-33, REQ-35
- **Подтверждающие фрагменты:** §7: «Авторизация действует только в текущем профиле браузера;»; §7: «Авторизованная сессия завершается после закрытия браузера;»
- **Описание проблемы:** раздел 7 опирается на поведение браузера (профиль, закрытие браузера), но перечень поддерживаемых браузеров и версий, а также требования к времени ответа при авторизации в источнике отсутствуют. Это отсутствие нефункциональных требований.
- **Влияние на разработку и тестирование:** проверки поведения `Remember me` и завершения сессии не имеют зафиксированной матрицы браузеров; проверки производительности формы авторизации не могут быть выведены из требований.
- **Вопрос:** какие браузеры и версии поддерживаются и какие требования к времени ответа при авторизации действуют?

### NB-13 — Не определено, какое значение Email сохраняется после неуспешной попытки

- **Класс:** `NON_BLOCKING`
- **Тип:** `AMBIGUITY`
- **Приоритет:** `LOW`
- **Связанные требования:** REQ-12, REQ-30 (AC-15)
- **Подтверждающие фрагменты:** §6: «Сохранить введённые значения в полях `Email` и `Password`.»; §3: «Перед проверкой пробелы в начале и конце Email удаляются.»
- **Описание проблемы:** требование говорит о сохранении «введённых значений», а нормализация Email предусматривает удаление пробелов по краям перед проверкой. Не определено, отображается ли после неуспешной попытки исходное значение с пробелами или нормализованное.
- **Влияние на разработку и тестирование:** проверка состояния поля после неуспешного входа не имеет единственного ожидаемого значения при вводе с пробелами по краям.
- **Вопрос:** отображается ли после неуспешной попытки исходное значение Email (с пробелами) или нормализованное (после удаления пробелов по краям)?

### NB-14 — Текст сообщения при нарушении формата не зафиксирован

- **Класс:** `NON_BLOCKING`
- **Тип:** `MISSING_INFORMATION`
- **Приоритет:** `MEDIUM`
- **Связанные требования:** REQ-13 … REQ-20, REQ-25 (AC-08, AC-09, AC-10, VR-05, VR-10, VR-13)
- **Подтверждающие фрагменты:**
  - §2: «При нажатии `Login` система проверяет оба поля и показывает все обнаруженные ошибки одновременно.»
  - §2: «При наличии ошибок запрос на авторизацию не отправляется.»
  - Тексты сообщений в SR-01 заданы только для двух случаев: «Это поле обязательно» (§2) и «Пароль должен содержать от 8 до 64 символов» (§4); для нарушений формата сообщений нет.
- **Описание проблемы:** решение ответственного лица по BLK-04 устранило неопределённость в части количества и факта сообщения при нарушениях формата Email: отображается одно общее сообщение, запрос не отправляется. Решение по BLK-02 определило, что символы вне белого списка — нарушение формата. При этом точный текст сообщения решением не задан ни для нарушений формата Email, ни для нарушения белого списка символов пароля. Эта остаточная неопределённость не влияет на решение о поведении системы, поэтому находка не блокирующая, но влияет на возможность проверять текст сообщения.
- **Влияние на разработку и тестирование:** разработка выбирает текст сообщения самостоятельно; тест-дизайн не может проверять точный текст, но может проверять факт отображения одного общего сообщения при нарушении формата Email и отсутствие отправки запроса. Для пароля остаётся неопределённым и наличие отдельного сообщения.
- **Вопрос:** какой текст имеет общее сообщение о нарушении формата Email и какое сообщение (и отображается ли оно) предусмотрено при нарушении белого списка символов пароля?
