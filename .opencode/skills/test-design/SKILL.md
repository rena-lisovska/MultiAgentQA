# Purpose

Skill определяет методологию проектирования тестовой модели на основании валидированного Requirement Review Artifact и контракт Test Model Artifact.

Skill отвечает только за содержание тестовой модели. Он не работает с Qase, не сохраняет файлы, не подтверждает создание тест-кейсов и не принимает решений о продолжении Workflow — это область ответственности Agent Instruction и Orchestrator.

# When to Apply

Skill применяется после прохождения Requirement Review Gate, когда подтверждённые требования нужно превратить в тестовую модель.

# Inputs

Обязательные:

- валидированный Requirement Review Artifact;
- область тестирования, определённая агентом (по умолчанию — весь Artifact).

Опциональные:

- ограничения тестирования;
- проектные правила приоритизации и соглашения об именовании тест-кейсов;
- существующие тест-кейсы и структура разделов Qase;
- сведения о корневом разделе Qase, внутри которого создаются Test Suites.

Если Artifact не позволяет определить ни одного требования в области тестирования, работа не выполняется.

# Context Filters

- использовать Requirement Review Artifact как единственный источник требований; не восстанавливать требования по памяти, по Confluence, по Jira-задачам или по существующим тест-кейсам;
- использовать разделы Artifact по назначению: `Acceptance Criteria` — основа Expected Result, `Validation Rules` — основа проверок валидации, `Boundaries` — основа граничных значений, `Dependencies` — основа интеграционных проверок, находки типа `RISK` — основа риск-ориентированного покрытия;
- отличать `EXPLICIT` и `DERIVED` критерии приёмки: тест на `DERIVED` критерий допустим, ссылка обязательна;
- не превращать `AMBIGUITY`, `CONFLICT` или `MISSING_INFORMATION` в тест-кейс с придуманным Expected Result;
- не использовать `RECOMMENDATION` из Requirement Review как требование;
- существующие тест-кейсы Qase использовать только для оценки покрытия и предотвращения дублирования;
- не загружать в контекст всю тестовую модель Qase, если достаточно релевантных тест-кейсов области тестирования.

# Procedure

1. **Определить область тестирования** (передана агентом).
2. **Определить Test Scope.** Разделить требования на покрываемые, исключённые и непокрываемые с причиной.
3. **Определить Test Strategy.** Выбрать техники и типы проверок по функциональным областям с обоснованием.
4. **Спланировать Test Suites** по разделу «Test Suite Rules».
5. **Оценить риски и критичность** по находкам типа `RISK` и значимости поведения.
6. **Спроектировать Test Scenarios**: намерение проверки, требования, раздел Qase.
7. **Спроектировать Test Cases** для каждого сценария: предусловия, шаги, Expected Result.
8. **Покрыть позитивные потоки**, следующие из требований.
9. **Покрыть негативные проверки**, предусмотренные требованиями и правилами валидации.
10. **Покрыть границы** в пределах значений, определённых требованиями.
11. **Добавить риск-ориентированные проверки**; такие кейсы помечаются `RISK_BASED`.
12. **Назначить приоритет** по разделу «Test Content Rules».
13. **Построить Traceability** для каждого требования области тестирования.
14. **Построить Risk Coverage** для существенных рисков.
15. **Проверить дубликаты** по разделу «Duplicate Detection».
16. **Сформировать Artifact** по разделу «Artifact Contract» и проверить по Completion Criteria.
17. **Применить Self-Refine** по `AGENTS.md` §9.

# Test Suite Rules

Test Suites отражают структуру тестовой модели в Qase и создаются по логическим блокам требований.

## Selecting blocks

- блок соответствует функциональной области или смысловому разделу требований;
- блок выделяется по требованиям, а не по типам проверок: `POSITIVE`, `NEGATIVE`, `BOUNDARY` остаются тест-кейсами внутри блока;
- блок покрывает замкнутую область поведения, чтобы тест-кейс однозначно относился к одному разделу;
- если в требованиях одна логическая область, создаётся один Test Suite;
- раздел без `READY`-тест-кейсов не создаётся.

## Hierarchy and naming

- по умолчанию один уровень вложенности под корневым разделом;
- вложенность допускается, только если в требованиях явно выделены подблоки;
- заголовок раздела — название логического блока без версий, дат и идентификаторов;
- заголовок уникален в пределах родительского раздела;
- родительский раздел создаётся раньше дочернего.

## Connection with requirements

- каждый Test Suite содержит перечень требований, которые в нём покрываются;
- требование не покрывается тест-кейсами из разных разделов без указания причины;
- Test Suite не добавляет требований и не расширяет Test Scope.

## Existing sections

- перед созданием раздела проверить, нет ли в Qase раздела с тем же заголовком и родителем: такой раздел переиспользуется;
- переиспользованный раздел фиксируется как `REUSE` с его `qase_suite_id`, новый — как `CREATE`;
- если существующий раздел лишь частично соответствует блоку, новый раздел не создаётся без решения ответственного лица.

# Test Scope Rules

- Test Scope строится только из требований Requirement Review Artifact;
- каждое требование области получает статус покрытия: `COVERED`, `PARTIAL`, `NOT_COVERABLE` или `OUT_OF_SCOPE`;
- `NOT_COVERABLE` указывается с причиной: блокирующая находка, отсутствующие данные, отсутствие проверяемого поведения;
- `OUT_OF_SCOPE` допускается только для требований вне переданной области; расширение за пределы Artifact не выполняется;
- ограничения тестирования фиксируются как часть Test Scope, а не как предположения.

# Coverage Rules

## Completeness

- каждый подтверждённый основной поток имеет хотя бы один позитивный тест-кейс;
- каждое правило валидации имеет проверку, если требования задают наблюдаемый эффект;
- каждое граничное значение имеет проверки на границе и за границей;
- негативные проверки создаются для ограничений, запретов и обязательных условий;
- интеграционные и state-transition проверки создаются только если требования задают зависимости или состояния;
- проверки обработки ошибок создаются только если требования задают поведение при ошибках.

## Techniques and types

`Equivalence Partitioning` и `Boundary Value Analysis` — техники выбора значений внутри тест-кейса, а не типы тест-кейсов.

Допустимые значения `test_type`:

- `POSITIVE` — подтверждённое успешное поведение;
- `NEGATIVE` — запрещённое, некорректное или неуспешное поведение;
- `BOUNDARY` — граничные значения и значения за границей;
- `VALIDATION` — правило валидации и его наблюдаемый эффект;
- `INTEGRATION` — взаимодействие требований или компонентов;
- `STATE_TRANSITION` — переход между состояниями;
- `ERROR_HANDLING` — обработка ошибок и исключений;
- `RISK_BASED` — проверка, добавленная по риску и не следующая дословно из требований.

Если проект Qase использует иной справочник типов, соответствие задаётся проектными правилами.

## Risk-based inspections

- `RISK_BASED` допускается только при ссылке на находку типа `RISK` в `related_risks`;
- такой тест-кейс не формулируется как новое бизнес-требование: Expected Result описывает наблюдаемую проверку, а не заявленное поведение продукта;
- если риск не требует отдельного тест-кейса, он фиксируется в Risk Coverage со ссылкой на покрывающие тест-кейсы.

# Test Content Rules

## Test Scenario

- `scenario_ref` — идентификатор в рамках Artifact (`SC-<nn>`);
- `title` — что проверяется;
- `intent` — зачем проверяется и какую часть требования покрывает;
- `source_requirements`;
- `related_risks` — для риск-ориентированного сценария;
- `case_refs` — перечень `test_ref`.

Сценарий описывает намерение и не содержит шагов и Expected Result: они принадлежат тест-кейсу. Один сценарий может объединять несколько тест-кейсов.

## Test Case

- `test_ref` — идентификатор в рамках Artifact (`TC-<nn>`);
- `scenario_ref`;
- `suite_ref` — раздел Qase (`SUITE-<nn>`);
- `title` — проверяемое поведение;
- `description` — краткая цель, если не очевидна из заголовка; не дублирует шаги и Expected Result;
- `preconditions` — только необходимые условия;
- `steps` — конкретные воспроизводимые действия;
- `expected_result` — наблюдаемый или измеримый результат; при опоре на критерий Artifact указывается ссылка `AC-xx`/`VR-xx`/`BR-xx`;
- `priority` и `priority_source`;
- `test_type`;
- `source_requirements`;
- `related_risks` — для `RISK_BASED`;
- `case_status` — `READY` или `BLOCKED`;
- `block_reason` и `open_questions` — для `BLOCKED`.

Правила:

- один тест-кейс проверяет одно поведение или одно условие;
- `preconditions`, `steps` и `expected_result` согласованы;
- тест-кейс не зависит от другого, если зависимость не обусловлена логикой процесса;
- тест-кейс без однозначного `expected_result` получает `BLOCKED`.

## Priority

Допустимые значения: `HIGH`, `MEDIUM`, `LOW`, `UNDEFINED`.

Приоритет отражает значимость проверки, а не сложность выполнения. Источник фиксируется в `priority_source`:

- `RISK_ANALYSIS` — следует из риска и критичности поведения;
- `REQUIREMENT_REVIEW` — следует из находок или рисков Artifact;
- `PROJECT_RULES` — задан проектными правилами;
- `UNDEFINED` — обоснования нет.

`HIGH` без обоснования риском, критичностью или проектным правилом не назначается.

## Case Status

- `READY` — тест-кейс пригоден к проверке дубликатов и созданию;
- `BLOCKED` — тест-кейс не может быть создан; причина в `block_reason`.

# Duplicate Detection

## Coincidence classes

- `EXACT` — то же поведение теми же условиями;
- `EQUIVALENT` — то же поведение, иная формулировка или структура шагов;
- `SIMILAR` — частичное пересечение проверяемого поведения;
- `RELATED` — общая функциональность, но иная проверка;
- `NOT_FOUND` — совпадений не обнаружено.

## Rules for solving

- `EXACT`, `EQUIVALENT` → тест-кейс не создаётся, `creation_status = DUPLICATE`, в `duplicate_reference` указывается `qase_case_id`;
- `SIMILAR` → решение по объёму: если существующий тест-кейс не покрывает поведение, тест-кейс создаётся, обоснование фиксируется;
- `RELATED`, `NOT_FOUND` → тест-кейс создаётся;
- совпадение названия не является основанием считать тест-кейсы дубликатами;
- если класс совпадения определить нельзя, тест-кейс получает `BLOCKED`.

# Artifact Contract

## Rules for filling out

- каждый раздел присутствует в Artifact;
- если результатов нет, раздел содержит `Не обнаружено` (`AGENTS.md` §7.1);
- спроектированный тест-кейс или раздел не считается созданным до подтверждённого ответа Qase Tool;
- `qase_case_id`, `qase_suite_id` и `creation_status` заполняются только по результатам фактических операций;
- Artifact не содержит тест-кейсов без исходного требования, без ссылки на сценарий и без раздела;
- Artifact не содержит Expected Result, не выводимого из Requirement Review, кроме `RISK_BASED` с указанной ссылкой на риск.

## Structure

**1. Header**

`artifact_name`, `artifact_version`, `date`, `producer`, `skill`, `application_name`, `qase_project`, `qase_suite`, `requirement_review_artifact`, `requirement_review_version`, `consumers`.

**2. Test Scope**

Область тестирования, ограничения, перечень требований со статусом покрытия и причинами.

**3. Test Strategy**

Применяемые техники и типы проверок по функциональным областям, обоснование, что сознательно не покрывается.

**4. Test Scenarios**

Поля сценария по разделу «Test Content Rules».

**5. Test Suites**

- `suite_ref` (`SUITE-<nn>`);
- `title`;
- `parent_ref` — при вложенности;
- `source_requirements`;
- `suite_decision` — `REUSE` или `CREATE`;
- `existing_suite_id` — при `REUSE`;
- `creation_status`;
- `qase_suite_id`;
- `error`.

**6. Test Cases**

Поля тест-кейса по разделу «Test Content Rules», а также:

- `duplicate_check_result`;
- `creation_status`;
- `qase_case_id`, `qase_case_url`;
- `duplicate_reference`;
- `skip_reason`;
- `error`.

Тест-кейсы `BLOCKED` не имеют `creation_status = CREATED`. Тест-кейс не имеет `creation_status = CREATED`, если его раздел не подтверждён.

**7. Traceability Matrix**

Для каждого требования области: `scenarios`, `cases`, `coverage_status` (`COVERED`, `PARTIAL`, `NOT_COVERABLE`), причина для `PARTIAL` и `NOT_COVERABLE`. Требование без записи означает незавершённое проектирование.

**8. Risk Coverage**

Идентификатор риска, покрывающие тест-кейсы, риски, которые невозможно покрыть, с причиной.

**9. Duplicate Check Results**

По каждому тест-кейсу: `test_ref`, класс совпадения, найденный `qase_case_id`, решение и обоснование. По каждому разделу: `suite_ref`, решение `REUSE` или `CREATE`, найденный `qase_suite_id`.

**10. Creation Summary**

Количество разделов и тест-кейсов по каждому `creation_status`, перечень созданных и переиспользованных разделов, перечень созданных тест-кейсов, дубликаты и пропущенные тест-кейсы с причинами, ошибки и неподтверждённые операции.

# Reasoning Patterns

**Self-Refine** (`AGENTS.md` §9) — проверить Artifact по Completion Criteria, исправить и проверить повторно.

**Branching / Tree** — при нескольких существенно разных стратегиях покрытия сформировать не более трёх вариантов, сравнить по полноте покрытия, риску и стоимости поддержки, выбрать обоснованный и зафиксировать причину в Test Strategy.

**Critic** (`AGENTS.md` §9) — искать требования без покрытия, тест-кейсы без Expected Result, придуманное поведение, необоснованные приоритеты, скрытые дубли и неподтверждённые результаты создания.

**Reviewer** (`AGENTS.md` §9) — если Workflow предусматривает независимого Reviewer, передавать ему Artifact и ссылки на источники, а не историю работы.

# Completion Criteria

- область тестирования зафиксирована;
- структура Test Suites определена по логическим блокам требований, каждый раздел имеет источник и хотя бы один `READY`-тест-кейс;
- каждый Test Case содержит `scenario_ref`, `suite_ref`, `preconditions`, `steps` и `expected_result`;
- каждое требование области имеет запись в Traceability Matrix со статусом покрытия;
- каждый Test Scenario связан с требованиями и содержит перечень тест-кейсов;
- Expected Result проверяем и выводится из Requirement Review либо помечен `RISK_BASED` со ссылкой на риск;
- позитивные и негативные проверки покрыты в пределах требований;
- правила валидации и границы покрыты там, где требования задают наблюдаемый эффект;
- приоритет и тип проверки имеют допустимые значения и обоснование;
- для каждого тест-кейса указан `case_status`, для `BLOCKED` — причина;
- для каждого `READY`-тест-кейса выполнен и зафиксирован поиск дубликатов;
- дубликаты не созданы повторно, решения по `SIMILAR` обоснованы;
- Artifact не содержит поведения, отсутствующего в Requirement Review;
- Artifact пригоден для создания тест-кейсов через Qase Tool в части `READY`-тест-кейсов.
