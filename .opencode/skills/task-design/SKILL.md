# Purpose

Skill определяет методологию преобразования валидированного Requirement Review Artifact в Jira Tasks Artifact и правила проектирования содержания задач.

Skill отвечает только за содержание работы. Он не работает с Jira, не сохраняет файлы, не подтверждает создание задач и не принимает решений о продолжении Workflow — это область ответственности Agent Instruction и Orchestrator.

# When to Apply

Skill применяется после прохождения Requirement Review Gate, когда требования нужно преобразовать в задачи разработки.

# Inputs

Обязательные:

- валидированный Requirement Review Artifact;
- область декомпозиции, определённая агентом (по умолчанию — весь Artifact).

Опциональные:

- проектные правила декомпозиции и соглашения об именовании;
- допустимые типы задач и другие проектные поля;
- тип головной задачи и поле связи с родителем;
- ограничения и приоритеты, переданные агентом;
- результаты проверки существующих Jira issues.

Если Artifact не позволяет определить ни одного требования в области декомпозиции, работа не выполняется: фиксируется отсутствие пригодных входных данных.

# Context Filters

- использовать Requirement Review Artifact как единственный источник требований; не восстанавливать требования по памяти, по тексту Confluence или по существующим Jira issues;
- использовать разделы Artifact по назначению: `Requirements` — объект декомпозиции, `Acceptance Criteria` и `Validation Rules` — основа критериев приёмки, `Dependencies` — основа зависимостей задач, находки типа `RISK` — основа приоритета и связанных рисков;
- не превращать `AMBIGUITY`, `CONFLICT` или `MISSING_INFORMATION` в задачу с придуманным поведением;
- не использовать `RECOMMENDATION` из Requirement Review как обязательное требование;
- при наличии нескольких версий Artifact использовать указанную версию и не смешивать версии;
- существующие Jira issues использовать только для предотвращения дублирования, не как подтверждение требования.

# Procedure

1. **Определить область декомпозиции.**
2. **Определить единицы работы.** Для каждого требования установить, требует ли оно отдельной работы команды разработки.
3. **Спроектировать головную задачу** по разделу «Parent Epic».
4. **Сгруппировать требования в дочерние задачи.** В одну задачу объединять требования с общей целью и общим проверяемым результатом.
5. **Проверить границы дочерних задач.** Разделять работу при разных целях, разных Acceptance Criteria, независимых рисках, разном объёме или возможности независимой поставки.
6. **Проверить отсутствие избыточного дробления.**
7. **Сформировать содержание каждой дочерней задачи** по разделу «Task Content Rules».
8. **Определить зависимости** между задачами и их характер.
9. **Определить приоритет** при наличии обоснования; иначе зафиксировать неопределённость.
10. **Отметить заблокированные задачи** статусом `BLOCKED` с причиной.
11. **Построить Traceability** для каждого требования области декомпозиции.
12. **Проверить дубликаты** по разделу «Duplicate Detection».
13. **Сформировать Artifact** по разделу «Artifact Contract» и проверить по Completion Criteria.
14. **Применить Self-Refine** по `AGENTS.md` §9.

# Parent Epic

Декомпозиция оформляется как иерархия: одна головная задача и входящие в неё дочерние задачи.

## Head Task

- тип задаётся правилом «Issue Type» и по умолчанию равен `EPIC`; значение `TASK` к головной задаче не применяется;
- `task_ref` — `EPIC-<nn>`;
- заголовок — название функциональности. Источник выбирается по порядку (первое найденное значение) и фиксируется в `title_source`:
  1. `application_name`, переданный агентом — `INPUT`;
  2. `application_name` из Header Requirement Review Artifact — `ARTIFACT`;
  3. `source_title` из Header Requirement Review Artifact — `ARTIFACT_SOURCE_TITLE`;
  4. заголовок страницы источника, переданный агентом — `INPUT_SOURCE_TITLE`;
- версии, даты, идентификаторы и служебные пометки в заголовок не добавляются;
- описание содержит только ссылку на требования: `requirements_source` с указанием страницы или раздела и путь с версией Artifact. Цель, объём работ, Acceptance Criteria и технические решения в описание не включаются;
- Acceptance Criteria для головной задачи не формируются;
- головная задача не покрывает требования в Traceability;
- если ни один из перечисленных источников не даёт названия функциональности, головная задача получает `BLOCKED`: заголовок не придумывается.

## Child Tasks

- каждая задача декомпозиции является дочерней;
- `parent_ref` = `task_ref` головной задачи;
- в Jira связь задаётся полем `epic_link_field` (`parent` или `Epic Link`) со значением `jira_issue_id` головной задачи;
- дочерняя задача не создаётся, пока создание головной задачи не подтверждено;
- если головная задача не создана и эквивалентный эпик не найден, дочерние задачи получают `SKIPPED` с причиной.

# Task Content Rules

## Title

- отражает результат работы, а не процесс;
- однозначен без чтения описания;
- не содержит номеров задач, названий спринтов и служебных пометок;
- уникален в пределах Artifact;
- не более 255 символов.

## Description

Содержит: контекст, функциональную цель, что требуется реализовать, ссылки на требования, ограничения из Artifact, зависимости от других задач.

Не содержит: технических решений и архитектуры, не подтверждённых требованиями; новых бизнес-правил; оценок сроков и трудозатрат.

## Acceptance Criteria

- каждый критерий описывает наблюдаемое или измеримое условие, однозначно определяющее выполнение задачи;
- критерий выводится из требований Artifact; при использовании критерия или правила указывается ссылка `AC-xx`/`VR-xx`/`BR-xx`;
- критерии не противоречат друг другу и не вводят нового поведения;
- субъективные формулировки не используются;
- если требование не позволяет сформулировать проверяемый критерий, задача получает `BLOCKED`.

## Source Requirements

Идентификатор требования и ссылка на место в источнике. Если задача покрывает несколько требований, перечисляются все. Задача без исходного требования не создаётся.

## Dependencies

Для каждой зависимости: связанная задача (`task_ref` или `jira_issue_id`), характер (`BLOCKS` — текущая задача не может быть начата до завершения указанной; `RELATED` — общая область без обязательного порядка; `NONE`) и причина.

Зависимость, не следующая из требований или переданного проектного контекста, не создаётся.

## Priority

Допустимые значения: `HIGH`, `MEDIUM`, `LOW`, `UNDEFINED`.

Источник фиксируется в `priority_source`:

- `REQUIREMENT_REVIEW` — следует из находок или рисков Artifact;
- `PROJECT_RULES` — задан проектными правилами;
- `ADDITIONAL_CONTEXT` — явно передан агентом;
- `UNDEFINED` — обоснования нет; приоритет требует внешнего решения.

`HIGH` без обоснования риском или критичностью не назначается.

## Issue Type

Тип задачи — поле Jira `issuetype` (`TASK`, `BUG`, `EPIC`, `STORY`, `SUBTASK` и другие значения схемы проекта).

Порядок определения (первое найденное значение), источник фиксируется в `issue_type_source`:

1. `jira_issue_type`, переданный агентом — `INPUT`;
2. проектные правила декомпозиции — `PROJECT_RULES`;
3. если тип не задан — `TASK`, `DEFAULT`.

Отсутствие заданного типа не блокирует задачу. Если Jira отклоняет тип, ошибка фиксируется (`creation_status = FAILED`), тип не подменяется самостоятельно.

Для головной задачи тип эпика задаётся явно и `TASK` не заменяется. Если типа эпика в схеме проекта нет, головная задача получает `BLOCKED`.

## Task Status

- `READY` — задача спроектирована и пригодна к проверке дубликатов и созданию;
- `BLOCKED` — задача не может быть создана; причина указывается в `block_reason`.

# Duplicate Detection

## Coincidence classes

- `EXACT` — та же работа с тем же объёмом;
- `EQUIVALENT` — та же работа, иная формулировка или иная декомпозиция внутри задачи;
- `SIMILAR` — пересечение объёма, но границы работ различаются;
- `RELATED` — общая область, но другой объём работ;
- `NOT_FOUND` — совпадений не обнаружено.

## Rules for solving

- `EXACT`, `EQUIVALENT` → задача не создаётся, `creation_status = DUPLICATE`, в `duplicate_reference` указывается `jira_issue_id`;
- `SIMILAR` → решение по объёму: если существующая задача не покрывает требование, задача создаётся; обоснование фиксируется в `duplicate_reference` или `skip_reason`;
- `RELATED`, `NOT_FOUND` → задача создаётся;
- совпадение названия не является основанием считать задачу дубликатом;
- если существующая задача закрыта или выполнена, а требование актуально, вопрос передаётся ответственному лицу: задача получает `BLOCKED`;
- если класс совпадения определить нельзя, задача получает `BLOCKED`.

## Head Task

- `EXACT`, `EQUIVALENT` → новый эпик не создаётся, в качестве родителя используется существующий, `creation_status = DUPLICATE`, `duplicate_reference` = его `jira_issue_id`;
- `SIMILAR` или класс не определяется → головная задача получает `BLOCKED`: две конкурирующие головные задачи не создаются;
- `NOT_FOUND` → головная задача создаётся.

# Artifact Contract

## Rules for filling out

- каждый раздел присутствует в Artifact;
- если результатов нет, раздел содержит `Не обнаружено` (`AGENTS.md` §7.1);
- спроектированная задача не считается созданной до подтверждённого ответа Jira Tool;
- `jira_issue_id`, `jira_issue_url` и `creation_status` заполняются только по результатам фактических операций;
- Artifact не содержит задач без исходного требования и задач, основанных на предположениях;
- Artifact не содержит технических решений, не подтверждённых требованиями.

## Structure

**1. Header**

`artifact_name`, `artifact_version`, `date`, `producer`, `skill`, `application_name`, `jira_project`, `requirement_review_artifact`, `requirement_review_version`, `consumers`.

**2. Decomposition Summary**

- область декомпозиции: что включено и что исключено;
- головная задача: `task_ref`, заголовок, `task_status`;
- количество дочерних задач, из них `READY` и `BLOCKED`;
- функциональные области;
- допущения и ограничения;
- перечень заблокированных задач с причинами.

**3. Parent Epic**

- `task_ref` — `EPIC-<nn>`;
- `title`; `title_source`;
- `description` — только ссылка на требования;
- `issue_type` и `issue_type_source`;
- `task_status`; `block_reason` для `BLOCKED`;
- `duplicate_check_result` и `duplicate_reference`;
- `creation_status`, `jira_issue_id`, `jira_issue_url`, `error`.

**4. Jira Tasks**

Для каждой дочерней задачи:

- `task_ref` (`TASK-<nn>`), `parent_ref`;
- `title`, `description`;
- `acceptance_criteria` со ссылками на `AC-xx`/`VR-xx`/`BR-xx`;
- `source_requirements`;
- `dependencies`;
- `related_risks`;
- `priority` и `priority_source`;
- `issue_type` и `issue_type_source`;
- `task_status`; `block_reason` и `open_questions` для `BLOCKED`;
- `duplicate_check_result`;
- `creation_status`;
- `jira_issue_id`, `jira_issue_url`;
- `duplicate_reference`, `skip_reason`, `error`.

Задачи `BLOCKED` не имеют `creation_status = CREATED`. Дочерние задачи не имеют `creation_status = CREATED`, если создание головной задачи не подтверждено.

**5. Dependency Map**

Зависимости `BLOCKS`, последовательность выполнения, задачи для независимого и параллельного выполнения.

**6. Traceability**

Для каждого требования области декомпозиции: `tasks`; либо `NO_TASK_NEEDED` с причиной; либо `NOT_DECOMPOSABLE` с указанием блокирующей находки. Требование без записи означает незавершённую декомпозицию. Головная задача требования не покрывает.

**7. Duplicate Check Results**

По головной и каждой дочерней задаче: `task_ref`, класс совпадения, найденный `jira_issue_id`, решение и обоснование.

**8. Creation Summary**

Количество задач по каждому `creation_status`, перечень созданных задач с `jira_issue_id`, дубликаты и пропущенные задачи с причинами, ошибки и неподтверждённые операции.

# Reasoning Patterns

**Branching / Tree** — при нескольких существенно разных вариантах декомпозиции сформировать не более трёх, сравнить по атомарности, трассируемости, зависимостям, риску дублирования и стоимости реализации, выбрать обоснованный и зафиксировать причину в Decomposition Summary.

**Self-Refine** (`AGENTS.md` §9) — проверить Artifact по Completion Criteria, исправить и проверить повторно.

**Critic** (`AGENTS.md` §9) — искать задачи без основания, потерянные требования, необоснованные Acceptance Criteria, скрытые зависимости, технические решения в описании и неподтверждённые результаты создания.

# Completion Criteria

- область декомпозиции зафиксирована;
- головная задача спроектирована: `task_ref` = `EPIC-<nn>`, заголовок с указанным `title_source`, описание — только ссылка на требования;
- для головной задачи выполнен и зафиксирован поиск дубликатов;
- каждая дочерняя задача содержит `parent_ref`;
- каждое требование области декомпозиции имеет запись в Traceability;
- каждая дочерняя задача имеет исходное требование, цель, границы и проверяемый результат;
- Acceptance Criteria проверяемы и не содержат придуманных бизнес-правил;
- зависимости обоснованы и не созданы искусственно;
- для каждой задачи указан `task_status`, для `BLOCKED` — причина;
- приоритет имеет обоснование и `priority_source` либо помечен `UNDEFINED`; тип задачи имеет `issue_type_source`;
- для каждой задачи `READY` выполнен и зафиксирован поиск дубликатов;
- дубликаты не созданы повторно, решения по `SIMILAR` обоснованы;
- созданные и несозданные задачи различимы, `jira_issue_id` присутствует только у подтверждённых;
- технические решения, не подтверждённые требованиями, отсутствуют;
- Artifact пригоден для создания задач через Jira Tool в части задач `READY`.
