# Purpose

Skill определяет методологию анализа и проверки качества требований и структуру Requirement Review Artifact.

Skill отвечает только за содержание анализа. Он не определяет полномочия агента, не работает с внешними системами, не сохраняет файлы и не принимает решений о продолжении Workflow — это область ответственности Agent Instruction и Orchestrator.

# When to Apply

Skill применяется при подготовке QA-ревью требований перед декомпозицией на задачи и проектированием тестовой модели.

# Inputs

Материалы, по которым выполняется анализ:

Обязательные:

- текст требований в пределах области анализа;
- границы области анализа, заданные агентом (что включено и что исключено).

Опциональные:

- идентификатор, заголовок, раздел и версия источника;
- критерии приёмки;
- связанные бизнес-правила и ограничения;
- определения терминов;
- описание существующего поведения системы;
- связанные документы, прямо относящиеся к анализируемой функциональности.

Если обязательных материалов нет либо они не позволяют определить ни одного требования, анализ не выполняется: фиксируется отсутствие входных данных, а не предположительное поведение.

# Context Filters

- использовать только материалы, относящиеся к области анализа;
- при наличии нескольких версий использовать более актуальную и не смешивать версии в одном выводе; признак устаревания фиксировать;
- не использовать предыдущие результаты анализа как источник требований, если требование можно проверить по исходному тексту;
- сохранять исходные формулировки и их разделы; пересказ допустим только как пояснение рядом с цитатой;
- сведения, полученные из контекста, а не из источника требований, помечать как контекст и не возводить в ранг требования;
- не включать в анализ функциональность, отсутствующую в источнике: её отсутствие — это пробел требований, а не разрешение додумать поведение.

# Procedure

1. **Зафиксировать область анализа.** Использовать область, переданную агентом. Расширять или сужать её Skill не вправе.
2. **Выделить требования.** Для каждого сохранить исходный текст и место в источнике; присвоить локальный идентификатор `REQ-<nn>`, если источник не содержит своих.
3. **Выделить бизнес-правила и ограничения.** Только те, что прямо следуют из текста требований.
4. **Выделить критерии приёмки.** Разделять `EXPLICIT` и `DERIVED` (проверяемые условия, выведенные из текста без добавления новых условий).
5. **Выделить правила валидации и граничные условия.** Для каждого правила указать наблюдаемый эффект и значения на границах.
6. **Выделить зависимости** между требованиями и связанными функциями; отметить зависимости без данных в источнике.
7. **Проверить согласованность (Consistency).** Несовместимые условия, взаимоисключающие результаты, конфликт бизнес-правил, расхождение между целью требования и описанным поведением.
8. **Проверить однозначность (Clarity).** Формулировки с несколькими трактовками, термины без определения, неопределённые субъекты и моменты времени, неоднозначные границы и приоритеты правил.
9. **Проверить полноту (Completeness).** Отсутствующие условия, результаты, состояния, сообщения, лимиты, обработка ошибок. Для каждого сценария проверить: что, когда, при каком условии, с каким результатом.
10. **Проверить тестируемость (Testability).** Для требования должна выводиться наблюдаемая или измеримая проверка; иначе — `TESTABILITY_GAP`.
11. **Проверить нефункциональную часть.** Если в источнике есть требования к производительности, безопасности, доступности, совместимости — проверить их измеримость. Если таких требований нет, зафиксировать их отсутствие как пробел, а не добавлять собственные.
12. **Определить позитивные и негативные потоки**, прямо следующие из требований.
13. **Классифицировать находки** по разделу «Findings Classification».
14. **Сформировать Artifact** по разделу «Artifact Contract» и проверить его по Completion Criteria.
15. **Применить Self-Refine** по `AGENTS.md` §9.

Порядок шагов 7–11 может выполняться итеративно по разделам требований; результат должен быть единым реестром находок без повторов одного и того же дефекта.

# Findings Classification

## Class

`BLOCKING` — если выполняется хотя бы одно условие:

- в требованиях к одним и тем же условиям заданы взаимоисключающие результаты (`CONFLICT`);
- ожидаемое поведение допускает несколько трактовок, и ни одна не следует из текста однозначно (`AMBIGUITY`);
- отсутствуют данные, без которых поведение определить нельзя (`MISSING_INFORMATION`);
- для требования нельзя вывести ни одного наблюдаемого или измеримого результата (`TESTABILITY_GAP`).

`NON_BLOCKING` — ожидаемое поведение определимо, но описание неполно, неточно или требует улучшения.

`RISK` и `RECOMMENDATION` всегда `NON_BLOCKING`.

## Type

- `CONFLICT` — взаимно несовместимые утверждения в требованиях либо между требованием и бизнес-правилом;
- `AMBIGUITY` — формулировка, допускающая несколько трактовок;
- `MISSING_INFORMATION` — отсутствие сведений, необходимых для определения поведения;
- `TESTABILITY_GAP` — отсутствие проверяемого результата или измеримого условия;
- `RISK` — потенциальное негативное следствие требования, не являющееся дефектом формулировки;
- `RECOMMENDATION` — предложение по улучшению формулировки без изменения смысла требования.

## Priority

- `HIGH` — затрагивает основной поток, безопасность, целостность данных или входную точку функциональности;
- `MEDIUM` — затрагивает второстепенный поток или отдельный граничный случай;
- `LOW` — локальное уточнение, не влияющее на определение поведения.

Приоритет отражает влияние на разработку и тестирование, а не класс находки.

## Required attributes of a find

- локальный идентификатор: `BLK-<nn>` для `BLOCKING`, `NB-<nn>` для `NON_BLOCKING`;
- класс, тип, приоритет;
- ссылка на требование и дословный фрагмент; для `CONFLICT` — все связанные требования;
- описание проблемы и объяснение, почему это проблема;
- влияние на разработку и тестирование;
- вопрос для уточнения — обязателен для `CONFLICT`, `AMBIGUITY`, `MISSING_INFORMATION`, `TESTABILITY_GAP`;
- рекомендация — обязательна для `RECOMMENDATION`.

Одна находка описывает один дефект. Одинаковый дефект, затрагивающий несколько требований, оформляется один раз со списком связанных требований.

# Artifact Contract

## Filling-out instructions

- каждый раздел присутствует в Artifact;
- если результатов нет, раздел содержит пометку `Не обнаружено` (`AGENTS.md` §7.1);
- существенный вывод сопровождается ссылкой на требование или источник;
- пересказ не заменяет цитату, если вывод основан на конкретной формулировке;
- Artifact не содержит требований, бизнес-правил и критериев приёмки без источника;
- риск или рекомендация не изложены в форме требования.

## Structure

**1. Header**

`artifact_name`, `artifact_version`, `date`, `producer`, `skill`, `application_name`, `requirements_source`, `source_title`, `source_version`, `consumers`, признак замены предыдущей версии.

`source_title` — заголовок страницы источника; если недоступен, указывается `не установлен`.

**2. Review Summary**

- область анализа: что включено и что исключено;
- источники: ссылка, заголовок, версия, дата, способ получения, статус верификации;
- краткий итог анализа;
- сводка находок по типам с количеством (для типа без находок — `Не обнаружено`);
- `requirements_readiness`: `READY` — нет `BLOCKING`-находок, `NOT_READY` — есть хотя бы одна. Значение отражает состояние требований, а не решение о продолжении Workflow.

**3. Requirements**

Локальный идентификатор, раздел источника, исходная формулировка, связанные бизнес-правила, `analysis_status` — `ANALYZED` или `NOT_ANALYZED` с причиной.

**4. Business Rules**

Идентификатор, правило, источник. Правило формулируется без условий, которых нет в тексте требований.

**5. Acceptance Criteria**

Идентификатор, проверяемое условие, источник, тип `EXPLICIT` или `DERIVED`, ссылка на находку, если проверка от неё зависит.

**6. Validation Rules**

Идентификатор, правило, наблюдаемый эффект, источник. Валидация формата описывается только в пределах, заданных требованием; недостающие элементы отражаются как находка.

**7. Boundaries**

Область, значения на границах и за границами, основание. Включаются только границы, выводимые из требований.

**8. Dependencies**

Идентификатор, зависимое требование, зависимость, наличие или отсутствие данных в источнике.

**9. Blocking Issues**

Находки класса `BLOCKING` с обязательными атрибутами.

**10. Non-blocking Issues**

Находки класса `NON_BLOCKING` с теми же атрибутами.

**11. Positive Flows**

Идентификатор, поток, ожидаемый результат, источник.

**12. Negative Flows**

Идентификатор, поток, ожидаемый результат, источник.

**13. Open Questions**

Вопросы к ответственному лицу: формулировка, связанная находка или требование, что будет уточнено. Вопросы не дублируют описание находок и не содержат вариантов решения, выданных за утверждённые.

**14. Review Conclusion**

- итоговая оценка состояния требований;
- перечень `BLOCKING`-находок;
- что остаётся неопределённым и какие части анализа от этого зависят;
- ограничения и условия для потребителей Artifact.

Раздел не содержит решения о запуске следующих этапов Workflow.

**15. Source References**

Перечень источников: идентификатор, ссылка, версия, дата, способ получения, статус верификации, какие разделы Artifact на них основаны.

# Reasoning Patterns

**Self-Refine** (`AGENTS.md` §9) — проверить Artifact по Completion Criteria, исправить и проверить повторно. Лимит итераций — `AGENTS.md` §9.

**Critic** (`AGENTS.md` §9) — оценивать Artifact как независимый рецензент: искать неподтверждённые утверждения, находки без источника, достроенное поведение, скрытые блокирующие неопределённости и потерю требований из области анализа.

**Branching / Tree** — по умолчанию не применяется. Если требование допускает несколько существенно разных трактовок, Skill не выбирает одну из них: трактовки фиксируются как часть находки `AMBIGUITY` или `CONFLICT` с вопросом для уточнения.

# Completion Criteria

- область анализа зафиксирована, и для каждого требования указан `analysis_status` с причиной для `NOT_ANALYZED`;
- явные требования, бизнес-правила и критерии приёмки выделены; выведенные критерии отмечены как `DERIVED`;
- каждая находка имеет класс, тип, приоритет, ссылку на требование и подтверждающий фрагмент;
- `CONFLICT`, `AMBIGUITY`, `MISSING_INFORMATION`, `TESTABILITY_GAP` либо зафиксированы, либо по типу указано `Не обнаружено`;
- приоритет назначен по влиянию, а не по типу находки;
- правила валидации и границы отражены там, где они следуют из требований;
- позитивные и негативные потоки определены в пределах доступных требований;
- риски отделены от требований и не сформулированы как обязательное поведение;
- открытые вопросы не дублируют находки и не содержат решения за ответственное лицо;
- все существенные выводы связаны с источником;
- Header содержит `source_title` либо пометку `не установлен`;
- Artifact не содержит требований, бизнес-правил, критериев приёмки или поведения без источника;
- Artifact пригоден для декомпозиции и тест-дизайна в части, не зависящей от `BLOCKING`-находок.
